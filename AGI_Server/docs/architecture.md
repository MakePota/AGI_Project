# AGI Server 架构

## 一句话定位

**薄转发层 + 任务镜像。** 它把前端的请求转给 `AGI_Agent`，把引擎的状态抄进数据库，
把引擎的事件流转给前端。**它不做任何智能体推理。**

为什么要有这一层、以及它的边界是怎么定的，见
[ADR 0014](../../AGI_Agent/docs/decisions/0014-split-server-and-agent.md)。

## 分层

```text
web/        对外接口。控制器只做三件事：收参数、调 service/agent、把异常交给统一处理器
  └─ task/  任务领域：实体、仓库、以及「什么时候去问引擎」这条唯一的判断
       └─ agent/  与 AGI_Agent 的跨服务契约与客户端（HTTP → 本服务的异常）
            └─ config/  配置绑定、WebClient、CORS、后台调度
```

| 包 | 责任 | 不该做的事 |
| --- | --- | --- |
| `web/` | HTTP 出入口；参数校验；统一异常 → 状态码 | 不写业务判断，不直接碰数据库 |
| `task/` | 任务的持久化与镜像逻辑 | 不直接发 HTTP（那是 `agent/` 的活） |
| `agent/` | 跨服务契约与调用；把 HTTP 状态码翻译成本服务的异常 | 不做业务判断，不认识数据库 |
| `config/` | 基础设施装配 | 不含业务逻辑 |

**为什么把契约单独放在 `agent/AgentContract`**：那是**跨语言接缝**。
Java 侧的 camelCase 与 Python 侧的 snake_case 在这里显式对齐（每个字段都标了
`@JsonProperty`），改它等于改对外接口——集中在一个人人知道要看的地方。

## 一条请求是怎么走完的

```text
POST /api/tasks
  ① 校验 goal（@Valid）
  ② 转发给引擎：POST /tasks
  ③ 把引擎的答复抄进 task 表（id 用引擎给的，本地不重新生成）
  ④ 返回 202 + 任务对象

GET /api/tasks/{id}/events        → 直接管道转发引擎的 SSE，本地不留任何流状态
POST /api/tasks/{id}/approval     → 转发决定 → 再抄一次最新状态
GET /api/tasks/{id}               → 未结束的任务先向引擎对齐一次，再返回
```

## 三条必须守住的规则

### 1. 执行状态的权威在引擎，这里只存镜像

计划、工具调用、审批记录都由 `AGI_Agent` 的 checkpointer 持有。
本地那张 `task` 表是**给用户看的镜像**：目标、状态、结果。

因此：**服务端绝不自己推断任务状态**，只抄引擎告诉它的。两边不一致时以引擎为准。
这条规则一旦破掉，就会出现"两个系统各说各话且无从对账"的局面。

### 2. 「什么时候去问引擎」只在一个地方决定

`TaskService` 里那一句 `if (!TaskStatuses.isTerminal(status))` 是**唯一**允许决定
"要不要去问上游"的地方。做法是：**读到未结束的任务就先对齐一次**。

这比后台轮询省事得多——没有常驻任务、没有要清理的状态、没有"轮询间隔该设多少"的问题；
代价是这次读取多一个 HTTP 调用（单人使用完全划算）。

**不认识的状态一律当作未结束**（`TaskStatuses`）：多问一次没有代价，
把进行中的任务误判成结束，用户就会看到一个永远停在中间的任务。

### 3. 事件流是管道，不是缓冲

SSE 端点把引擎的流原样转给前端，本地不重放、不缓冲、不加工。
事件的历史由引擎侧的有界缓冲负责，断线续传靠 `since` 参数向引擎要
（[ADR 0015](../../AGI_Agent/docs/decisions/0015-interrupt-as-queryable-state.md)）。
这样服务端**没有任何要跟着清理的流状态**。

三件必须做对的事：

- **自己发心跳**（15 秒一次）。引擎的 `: keep-alive` 注释行在半路会被 SSE 编解码器丢掉，
  而任务停下等人批准时可能几分钟没有数据——中间的代理会把空闲连接当死连接掐掉。
- **客户端断开时取消上游订阅**。上游是会花钱的模型调用，继续为一个没人看的流保持连接等于持续烧钱。
- **不给上游加读超时**。空闲不等于故障（见 `WebClientConfig` 的注释）。

## 持久化

- **表结构由 Flyway 管**，JPA 只做校验（`ddl-auto: validate`）。
  不许用 `update` 让 Hibernate 自动改表——改动没有记录，而且会在你没注意时删列改列。
- **迁移脚本不许改**：Flyway 校验已执行脚本的校验和，改了它会让所有环境的启动直接失败
  （这是有意的保护）。要改结构就新增 `V2__*.sql`。
- **`task.user_id` 现在就存在**，值固定。真做登录时只是换个值，不需要改表、也不需要迁移存量数据。
- **没有事件表**，是刻意的：服务端不存事件。触发条件是"真要做任务历史详情页"。

## 错误怎么映射

按"调用方该怎么办"分配，而不是按异常类型堆砌：

| 状态码 | 含义 | 典型来源 |
| --- | --- | --- |
| 400 | **你给的东西不对** | 参数校验失败、不是图片的文件、引擎判定的入参问题 |
| 404 | 那个任务不存在 | 引擎回 404 |
| 409 | 状态冲突，**先重新拉一次状态** | 对已结束/已处理的任务再提交审批 |
| 413 | 超过本服务的接收上限 | Spring 的 multipart 限制 |
| 503 | **不是你的错**，引擎不可用 | 连不上引擎、引擎 5xx |

**400 与 503 必须分开**：前者是"你改一下再试"，后者是"服务没起来"。
把它们都压成 500，排查方向会完全跑偏。

## 技术栈

| 领域 | 选型 | 说明 |
| --- | --- | --- |
| 语言/运行时 | Java 21 LTS | |
| 框架 | Spring Boot 4.1 | 注意 4.x 把自动配置拆成了独立模块，见 README 的"踩过的坑" |
| Web | Spring MVC + `SseEmitter` | 低并发，不需要 WebFlux 的响应式复杂度 |
| 对上游调用 | `WebClient` | 只作为客户端用，用来消费 SSE |
| 持久化 | Spring Data JPA + MySQL 8 | 表结构由 Flyway 管 |
| 数据库运行方式 | Docker Compose | 同一份 compose 以后能搬到服务器 |

选型理由与被否决的方案见
[ADR 0016](../../AGI_Agent/docs/decisions/0016-server-stack-selection.md)。
