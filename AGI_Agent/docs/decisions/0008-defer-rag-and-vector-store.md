# 0008 本阶段不引入 RAG 与向量数据库

- 日期：2026-10-12
- 状态：已决定（可重审，重审条件见「后果」）

## 背景

「要不要上 RAG」在这类项目里几乎一定会被问到，而且越早做越像「架构完整」。
需要判断它对**当前**的瓶颈是否有帮助。

## 决策

**本阶段不引入 RAG，也不引入向量数据库。**

## 被否决的方案

- **现在就上 RAG**：RAG 解决的是「模型不知道的事实太多、塞不进 prompt」。
  当前任务的瓶颈是「**无法操作微信与 Steam**」，属于**工具能力**问题，检索替代不了。
  而且当前**没有可检索的语料**——RAG 会先建一套基础设施，再来找它要解决的问题。
- **为了让 checkpointer 和 RAG 共用 Postgres 而提前引入 Postgres**：
  属于为将来的便利提前付运维成本。

## 后果

- **重新审视的触发条件**（出现任一再评估）：本地文件检索与总结、长期记忆、
  网页查询结果沉淀复用。
- **注意定位**：这些在项目愿景里属于**后续独立的 Skill/Tool 能力**，
  将来应作为 `tools/` 下的能力接入，**而不是先改造数据库层**。顺序反了会白做——
  先建了向量库，最后发现真正需要的是一个「读取并总结本地文档」的工具。
- 路径是通的：若将来 RAG 与 checkpointer 都需要 Postgres，可用 `pgvector` 扩展共用一个实例
  （见 ADR 0004 关于 Redis 的评估）。但这只是运维层面的省事，不代表两者在架构上耦合。
- **文档检索不属于本条限制**：本项目的设计文档（`docs/`）体量小，用目录索引 + 文本检索
  已经足够，且**比 RAG 更精确**——RAG 会把一段论证切成几块、只召回其中一块，
  而这恰恰会丢掉最需要的「为什么」。

  把文档作为语料引入向量检索的**具体触发条件**（出现任一即重新评估）：

  1. `docs/features/README.md` 的索引表超过一屏（约 40-50 条）；
  2. 你或 AI 出现「不确定该读哪一篇」的情况；
  3. 为了回答一个问题，需要连读 3 篇以上文档。

  在此之前，任何形式的向量检索都是净负担。届时设计文档是理想的 RAG 语料
  （语义密度高、变化慢），而**代码恰恰相反**（变化快、切块噪音大），不纳入。
