# 0011 前提条件不满足时停下，不进重规划

- 日期：2026-10-12
- 状态：已采用
- 触发原因：真实使用反馈

## 背景

用户断掉代理后实测，遇到两个问题：

1. **查价格等了 45 秒毫无输出。** `page.goto` 用的是默认超时（45 秒），
   而 CLI 只在最后打印一次回复——窗口全程不动。
2. **加购/删除报的是「结果不确定」**，用户困惑：明明是网络不可达。

第 2 条的机制值得记下来：**点击是一个本地动作**。`link.click()` 作用在已经渲染好的
元素上，**不需要网络**，所以网络断了它照样"成功"。因此"点到了"完全不能证明网络是好的。

而在**点击之后**，我们确实无法区分「POST 没发出去」和「POST 发出去了但没听到回应」——
所以那一刻报「结果不确定」是**对的**（见 ADR 0010），**不能**改成「网络不可达」。

但复盘出两个真问题：

- **缺少前置探测**：写操作前没有确认通路。旁证很有说服力——planner 在重规划时
  自己生成了「先用只读搜索探测 Steam 商店当前是否可达（上次失败的根因是代理/网络不可达）」
  这一步。模型在替工具补它该做的事，说明这道闸就该建在工具里。
- **网络问题被归成了普通失败**：普通失败是可重试的，于是 planner 白跑几轮重规划——
  而「代理没开」这件事重规划一百次也修不好。

## 决策

新增**第三类**失败结局，专门表示「确定没做，但重规划也修不好」。

一次工具调用的结局现在是四类，判据是**「谁来修」**：

| 结局 | 含义 | 谁来修 |
| --- | --- | --- |
| 成功 | 确认生效 | — |
| `FAILED` | 确定没做成，**计划的问题** | planner 重规划或许能成 |
| `PRECONDITION_FAILED` | 确定没做成，**环境的问题** | 只有人能修（开代理、重新登录） |
| `OUTCOME_UNKNOWN` | 可能做了，不知道 | 只有人能核实 |

落地：

- `tools/errors.py` 新增 `PreconditionError`；`ToolCallStatus.PRECONDITION_FAILED`；
  `route_after_execute` 把它和 `OUTCOME_UNKNOWN` 一起归入 `halt`。
- **前置探测**：每个工具开头用 **8 秒**超时探一次商店首页。不通立刻报错，
  不让用户对着一个 45 秒不动的窗口（实测 45 秒 → 8.6 秒）。
- **网络错误一律归为 `PreconditionError`**。超时单独措辞——「代理程序开着但上游不通」
  正是这个表现，与「代理根本没开」（会立刻失败）是两种不同的病。
- **登录态检测**：落在 `/login/`，或购物车读出空且本地已无登录 cookie → 判定过期，
  明确要求重新扫码。**只检测，绝不续期**（ADR 0006）。
  关键点是它发生在**点击之前**，所以结论是"确定没做"。
- CLI 改为**流式输出**，工具调用在**开始之前**就打一行（`get_stream_writer`）。

## 被否决的方案

- **点击之后把结果改报成「网络不可达」**：会在 POST 真的发出去时撒谎，
  正是 ADR 0010 要防的那种错。点击之后只能报不确定。
- **只发个警告，仍按普通失败处理**：planner 会重规划。实测中它确实重试了，
  用户最终拿到的是"任务未完成"，而不是"请开代理"。
- **让 reviewer 判断"这个失败该不该重试"**：把确定性规则交给语言模型，还多花一次调用。
- **把 `PreconditionError` 并入 `UncertainOutcomeError`**：两者对用户的要求**完全相反**——
  一个要"去核实是否已经生效"，一个要"去修好环境再重来"。合并会让用户不知道该做什么。
- **每次运行前强制要求用户手动验证登录**：实测反馈明确拒绝——「我不可能每次查询都要
  去手动看看登录是否过期」。正确做法是**在使用时自动检测**并给出下一步动作。

## 后果

- `respond` 必须能同时呈现两类中断（可能同时发生），且措辞不能混。已实现并有测试。
- **新增工具时必须想清楚它的失败属于哪一类。** 判据是「谁来修」：
  计划的问题 → `ToolError`；环境的问题 → `PreconditionError`；不知道做没做 → `UncertainOutcomeError`。
- 整个过程必须可见。一次工具调用可能跑几十秒，没有输出用户会当成卡死——
  这不是体验问题，实测中它直接导致用户以为程序没反应。**这一条适用于所有长耗时工具。**
- 遗留：`PRECONDITION_FAILED` 目前仍与不确定结局共用 `TaskStatus.NEEDS_HUMAN`。
  用户可见的措辞区分了，但状态枚举没区分。将来若需要按状态统计失败类型，应该拆开。
