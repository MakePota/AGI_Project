# 0016 服务化选型：Java/Spring、MySQL、uni-app、SSE

- 日期：2026-10-13
- 状态：已采用

## 背景

要做界面，就得定后端语言与框架、前端框架、数据库、以及前后端之间的传输方式。这次选型与前面几次不同：**用户明确把这当作一次技术栈练习**（"为什么不在自己的项目里实践一遍企业里真正在用的东西"），所以"练手价值"在这里是一个**正当的决策依据**，而不只是"项目当下需不需要"。

同时必须警惕另一件事：练手价值很容易变成"把以后可能用到的组件都先堆进来"。因此本 ADR 对**不引入的组件逐条写明触发条件**——没有触发条件的东西不许以"以后可能用得上"的名义进来。

## 决策

| 位置 | 选型 |
| --- | --- |
| 业务后端 | **Java 21 LTS + Spring Boot 3 + Maven** |
| Web 层 | **Spring MVC + `SseEmitter`**（不上 WebFlux） |
| 数据库 | **MySQL**（第一版只用它） |
| 前端 | **uni-app（Vue 3）** |
| 前后端传输 | **SSE** |
| Agent 侧 API | **FastAPI**（Python，见 ADR 0014） |

### 明确推迟的组件与触发条件

| 组件 | 什么时候才该上（任一成立） |
| --- | --- |
| **MongoDB** | 需要对事件 payload 内部字段做聚合分析；或事件量到百万级；或需要 TTL 自动过期；或事件结构频繁变动。**目前一条都不成立**——事件按任务线性增长，单人使用几年也到不了百万级 |
| **Redis** | ① **要做多任务并发**（checkpointer 从 SQLite 换成它，ADR 0004 已写明，且必须开 AOF）——这是最明确的一条；② 需要跨进程的锁/幂等闸门；③ 需要给模型调用装限流闸门（**目前工具调用没有任何配额**，只限制了重规划次数）；④ 缓存外部查询（Steam 搜索/价格）；⑤ 多客户端广播 |
| **Qdrant / Milvus** | 真出现 RAG 需求时。且到那时**先定「怎么判断它答得对」，再定切分与检索策略，最后才选向量库**——RAG 的成败八成不在向量库选型。百万级以内推荐 Qdrant；文档量很小时关键词检索就够（Karpathy 本人的建议）；> 1 亿向量或存在 QPS/延迟硬指标才轮到 Milvus |

## 被否决的方案

- **FastAPI 做业务后端**。用户在别的项目里已经用过 FastAPI，而企业环境里 Java 后端仍占多数；这个位置（用户、数据库、网关）正是最值得练的地方。**代价必须说清**：首版 Java 层几乎全是管道（转发、存库、中继），难的智能部分仍在 Python。这是「业务服务调用 AI 能力」的真实形态，不是设计缺陷，但事先要知道。

- **WebFlux（响应式）**。它能在几十个线程上扛上万条长连接，并自带背压与取消。但我们是**单人使用、低并发**，为此付出响应式编程的复杂度不划算——2026 年已有同类项目按同样理由选了 MVC + `SseEmitter`，并留出「将来需要再换」的接缝。

- **WebSocket 或轮询**。轮询省事但差在「以后」；WebSocket 多一条有状态连接，而本项目的审批语义**不依赖连接**（ADR 0015），用它承载是把简单问题做复杂。SSE 是 AI 应用的既成事实（OpenAI / Anthropic 的流式接口都是它），且复用 HTTP、自带重连。

- **PostgreSQL**。pgvector 与 JSONB 确实各有优势，但在**本项目的数据量下，两者的技术差异被明显夸大**（真正差别是 JSONB vs JSON，以及一些 MVCC 细节）。既然练手价值是正当依据，就选更贴合预期练习环境的 MySQL。真正需要向量时，按上表的触发条件单独决定，那时无论选 Qdrant 还是 pgvector 都不需要重做数据层。

- **uni-app X**。性能接近原生，但转译器是黑盒、类型系统有阉割（Kotlin/Swift 没有 `undefined`）、生态与文档远不如传统版；而且它**并不覆盖 Windows 桌面**——用户说的"跨平台"里那条"桌面"，两个 uni-app 都给不了。对我们这种只有简单交互的界面，传统版的 WebView 天花板碰不到。**桌面端暂以浏览器打开代替。**

- **原生 HTML/JS 或 React**。用户目标包含以后做安卓 App，纯网页等于白费功夫；React 则要为「一个输入框 + 一个列表 + 一个审批面板」引入整套 Node 构建链。

- **LangGraph 官方 Server**。见 ADR 0014。

## 后果

- **几个实践要点不是可选项**（都来自调研，漏掉会出真问题）：Tomcat 异步请求默认超时只有 **30 秒**，必须显式调大；要按约 15 秒发心跳，避免代理/负载均衡掐掉空闲连接；`onCompletion`/`onTimeout` 里**必须**摘掉 emitter，否则内存泄漏；**客户端断开时要取消上游调用**——上游是会花钱的模型调用。

- **App 端没有 `EventSource`**。uni-app 的 App 端不是浏览器环境，打包安卓时需要接原生插件或 renderjs 桥接，且 `uni.request` 的 `enableChunked` 会被缓冲（表现为"打字机效果"变成整段弹出）。第一版按 H5 做，**这笔代价已知并推迟**；因为契约是窄的（ADR 0015），届时只需改前端收数据那一段。

- **MySQL 是唯一存储，所以没有跨库一致性问题**。这是选单库的隐性收益：多语言持久化（MySQL + MongoDB + Redis）真正的麻烦不在装组件，而在**跨库没有事务**，得自己上 Saga/Outbox。

- **重新审视的条件**：并发任务（→ 换 checkpointer 到 Redis）、事件分析型查询（→ MongoDB）、真做 RAG（→ Qdrant）。
