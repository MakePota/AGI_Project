# 0010 结果不确定的写操作不得自动重试

- 日期：2026-10-12
- 状态：已采用
- 触发原因：一次真实事故

## 背景

在一次真实的 Steam 加购测试中，购物车里出现了 **3 份同一个游戏**，而 Agent 全程报告的
是「失败」。还原出的过程：

```text
未开代理 → 搜索页 net::ERR_EMPTY_RESPONSE（此时确实什么都没发生）
   ↓ 某一轮网络恰好通了
点击「加入购物车」→ 真的加进去了
   ↓ 紧接着读购物车失败（网络中断 / React 还没渲染完）
工具判定"复核失败" → 报成"操作失败"
   ↓ planner 看到失败，重新规划
再次执行 → 又加一次
   ↓ MAX_REVISIONS = 3
购物车里 3 份
```

**整条链路没有崩溃、没有异常，只有一句看起来完全合理的失败文案。**

复盘时发现两个独立成因，它们收敛成了同一个错误结论：

1. 网络中断，购物车页根本打不开；
2. 复核用的等待时间不够——购物车页是 React 应用，旧实现用
   `domcontentloaded + 1.2 秒`就读页面文本，React 还没画完，
   于是"找不到该游戏"被当成"没加上"。

真正的根因不在这两个成因里，而在于**「验证不了」被当成了「操作失败」**。

## 决策

把工具调用的结局从两种改成**三种**，并让图尊重第三种：

| 结局 | 含义 | 允许重试 |
| --- | --- | --- |
| 成功 | 确认生效 | — |
| 明确失败 | **确定没有产生副作用** | ✅ 可以 |
| **结果不确定** | 可能已生效，但无法确认 | ❌ **禁止** |

落地为三处：

- `tools/errors.py` 的 `UncertainOutcomeError`——工具用它声明"我不是失败，我是不知道"。
- `ToolCallStatus.OUTCOME_UNKNOWN`——执行记录里必须能区分这两种结局。
- `graph/builder.py` 的 `route_after_execute`——一旦出现不确定，**直接跳到 respond**，
  不进 reviewer、**更不进重规划**。`executor` 同时中止剩余步骤。

配套两条实施纪律，写进 `steam.py`：

- **动作发生之后，任何失败都必须报成"结果不确定"。** 包括读取失败、复核失败、
  点击之后抛错。
- **复核可以重试，动作不可以。** 复核要反复读直到确认或超时（`_poll_cart`），
  因为慢半拍是常态；但动作绝不重放。

## 被否决的方案

- **只做幂等、不加"不确定"这一层**：幂等能挡住重复加购，但挡不住所有写操作。
  **发一条微信消息无法幂等**——它没有"已经发过了"这种状态可以查。
  所以这一层是必须的架构能力，不能只靠每个工具自觉。
- **让 reviewer 判断该不该重试**：把安全边界交给一个语言模型，而且要多花一次调用。
  这是确定性的规则，不该由模型决定。
- **出现不确定就整体失败退出**：会把"可能成功了"和"确定失败"混为一谈，
  用户看到的状态是错的。
- **无限重试复核**：会卡住任务。给复核一个超时（当前 20 秒），超时才报不确定。

## 后果

- 不确定的结果会以 `TaskStatus.NEEDS_HUMAN` 结束，回复里明确写出
  **哪些动作可能已经生效**，并要求人工核实——而不是给一句"任务未完成"。
- 每次写工具的失败路径都要想清楚它属于哪一类。**拿不准时选"不确定"**：
  多打扰用户一次，好过在真实世界里留下一份没人知道的副作用。
- 新增了一个需要维护的不变量：`executor` 里 `except UncertainOutcomeError`
  必须排在 `except Exception` 之前（它是 `ToolError` 的子类）。
  `tests/unit/test_uncertain_outcome.py` 锁住了这条链路。
- **幂等仍然要做**，它是第二道闸：即使某处误判成"确定失败"并重试，
  幂等的工具也不会重复执行。两道闸的关系是互补，不是替代。
