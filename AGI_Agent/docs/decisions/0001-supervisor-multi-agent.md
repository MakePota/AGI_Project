# 0001 多 Agent 采用中心化 Supervisor 模式

- 日期：2026-10-12
- 状态：已采用

## 背景

最初的实现只有一个 `conversation` 角色：把用户输入交给模型，打印回复。

要支撑「理解任务 → 规划 → 执行 → 审查 → 回复」的多步流程，并且允许审查不通过时重新规划，
必须先决定多个 Agent 之间如何组织。约束有两个：模型调用真实计费，能省则省；
「规划」需要判断力，「执行」偏机械，两者对模型能力的要求不同。

## 决策

**中心化协调（Supervisor）**：一个中心节点负责决策与调度，其余角色作为 worker 被指派、向中心汇报，
而不是平级 Agent 之间互相对话。

| 角色 | 职责 | 能力等级 |
| --- | --- | --- |
| `conversation` | 语义理解与直接对话回复 | 普通 |
| `planner` | 分诊 + 规划 + 调度（Supervisor 本体） | 最强 |
| `executor` | 执行具体步骤与工具调用 | 普通 |
| `reviewer` | 审查执行结果，不合格则打回 `planner` | 较强 |

**分诊（判断这是闲聊还是任务）由 `planner` 在第一步完成**，不由 `conversation` 承担。

```text
用户输入
  └─ planner 分诊（最强）
       ├─ 闲聊 ─> conversation（普通）─> 回复
       └─ 任务 ─> planner 规划 ─> executor（普通）─> reviewer（较强）
                                                       │
                                          ┌── 通过 ────┴─> 回复
                                          └── 不通过 ───> 回到 planner 重新规划
```

## 被否决的方案

- **平级 Agent 互相对话（去中心化）**：协调成本高；出问题时难以判定责任在哪个角色；
  token 消耗不可控（每轮都要广播）。对本项目的规模，收益为负。
- **单一 Agent 从头做到尾**：无法把「规划」与「执行」分开审查——而本项目要求计划必须
  人类可读、可审批（见 ADR 0006 的判据）。而且角色与模型无法分级绑定，贵的地方省不下来。
- **分诊交给 `conversation`，省下强模型的一次调用**：否。分诊决定后续走哪条分支，
  判错的代价远大于省下来的那一次调用。

## 后果

- **已知代价**：纯闲聊也需要一次强模型调用。接受，理由是判错代价更高。
- **角色与模型解耦**：角色只定义能力等级，具体模型由配置绑定（见 ADR 0002）。
  换掉「planner 用哪个模型」不影响图的代码。
- 一次任务最多重规划 3 次（`MAX_REVISIONS`）。**必须有上限**：`planner` 与 `reviewer`
  可以互相打回，没有封顶就是死循环，而且每轮都在花钱。
- 审查打回的是**计划**，不只是执行结果。因此 `PlanStep`（意图）与 `ToolCall`（实际执行记录）
  分开保存在状态里。
