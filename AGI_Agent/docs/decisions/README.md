# Architecture Decision Records（ADR）

本目录记录**会影响长期演进的技术决策**：当时面临什么、选了什么、否决了什么、代价是什么。

它回答的是「**为什么是这个样子**」。至于「这个功能怎么运转」写在 [`../features/`](../features/)，
「项目整体长什么样」写在 [`../architecture.md`](../architecture.md)。

## AI 读取约定

**不要一次读完整个 `decisions/`。** ADR 是**档案**，不是教材——它们的存在是为了将来某一天被查到。

1. 先读下面的目录表（应该在一屏之内），判断哪 **1-2 篇**与当前任务相关。
2. 只打开那几篇。
3. 如果没有一篇看起来相关，那就是**真的不相关**，不要「顺便都读一遍」。

赶时间的话，每篇的 `## 决策` 一节本身就是摘要，只读那一节通常就够。

## 什么时候该写一篇

- 引入、移除或替换一个依赖、框架、外部服务
- 在两个及以上方案之间做过取舍
- 定下一条**将来会被重新提起**的规则（例如「本阶段不引入 RAG」）
- 划定了子项目之间的边界

不必为了写而写。一次性的、没有替代方案的实现细节，属于代码注释或功能文档，不属于这里。

## 格式

命名：`NNNN-短横线小写标题.md`，编号递增，**不复用、不重排**——其他文档和提交信息会引用编号，
重新编号会让所有链接失效。

每篇四个小节，缺一不可：

| 小节 | 写什么 |
| --- | --- |
| `## 背景` | 当时面对什么问题，有哪些约束 |
| `## 决策` | 选了什么，一句话能说清 |
| `## 被否决的方案` | 考虑过哪些、为什么否掉 |
| `## 后果` | 代价、已知局限、什么条件下应该重新审视 |

**`被否决的方案` 是最值钱的一节。** 半年后你一定会重新想到那个被否掉的方案，
这一节是唯一能拦住你重走一遍的东西。没有它，这篇 ADR 只剩一半价值。
