# 0012 图像理解走千问，档位由工具与配置决定

- 日期：2026-10-13
- 状态：已采用

> 2026-10-20 补充：图片生成也走千问，但那是**另一个工具、另一个槽位**
> （`image.generate` / `Role.IMAGE_GENERATION`），见 [ADR 0018](0018-image-generation-with-artifacts.md)。
> 本篇关于图像理解的决策不受影响；“千问只做图像理解”应理解为“千问不接管文本角色”。

## 背景

Agent 需要「看懂图片」。有两条路：让某个 agent **角色**改用多模态模型，或者新增一个
**工具**、由工具内部调用多模态模型。

外部约束有三条：

1. 主力模型 DeepSeek 不支持图像输入，而用户希望**只在需要图像理解时才调用千问**，
   日常文本推理继续走 DeepSeek。
2. 用户明确要求：简单任务用 Flash、复杂任务用 Max，且**档位必须可预测、可审计**，
   不接受「让模型自己判断该用哪个模型」。
3. 千问的 `qwen3.8-flash` / `qwen3.8-max` 都是原生多模态，并提供 OpenAI 兼容端点——
   于是接入不需要新的模型适配器，ADR 0002「角色 → 配置」的设计在这里兑现。

## 决策

1. **千问只做图像理解**，不接管任何 agent 角色。新增两个工具，各绑定一个模型槽位：

   | 工具 | 槽位 | 模型 |
   | --- | --- | --- |
   | `vision.describe_image` | `Role.VISION_QUICK` | `qwen3.8-flash` |
   | `vision.analyze_image` | `Role.VISION_DEEP` | `qwen3.8-max` |

2. **档位是「工具名 → 槽位 → 模型」两级静态绑定，不进入计划参数。**
   模型在计划里只能选工具名，填不了档位；换模型只改 `config.toml`。

3. **两个工具都是 `RiskLevel.WRITE`。** 读图会把本地图片字节上传到阿里云，属于数据外发，
   必须由人过目一次——复用 `authorize` 的整批审批中断，不需要在策略层加特判。
   若将来嫌确认太频繁，改回 `READ` 只是注册表里的一行改动。

4. **思考模式按档位显式写进配置**：Flash 关、Max 开。为此给 `ModelSpec` 增加可选的
   `extra_body` 透传字段。

5. **读图不使用 `UncertainOutcomeError`**：它没有副作用，不存在「可能已经改动了什么」。
   本地文件问题 → `ToolError`（可重规划）；环境/配置问题 → `PreconditionError`（停下问人）。

## 被否决的方案

- **一个工具带 `tier` 参数。** `tier` 会由 planner 在计划里填出来，就是「让模型自报档位」，
  直接违反上面的第 2 条约束；而且它与 ADR 0007 要封死的形状相同——能力的关键属性由模型
  输出决定，配置无法单独回答「这次会用哪个模型」。

  需要诚实承认：**两个工具的写法里，planner 仍然要在两者之间选，因此间接决定了模型。**
  区别在**决策面**：它选的是一个具名能力（其模型绑定是注册表的静态属性），
  而不是把一个档位值当参数吐出来。这与 ADR 0007 里「planner 选工具、policies 赋 risk」
  是同一个分工。

- **新造一套 `VisionTier` 枚举加专用 loader。** 等于把「槽位 → ModelSpec」重造一遍，
  多一层维护面，且没有带来任何两个工具做不到的能力。

- **在工具里硬编码模型字符串。** 档位立刻变得不可配置，违反第 2 条约束。

- **把千问作为主力文本模型。** 用户明确只要图像理解；主力文本推理继续由 DeepSeek 承担，
  避免为了一个能力顺带换掉整条链路。

- **改走 DashScope 原生 multimodal 端点。** 兼容端点实测能吃 base64 图（见「后果」），
  没有理由为此多写一个适配器。

- **不做任何修改就让人审批。** 这里牵连出一个既有漏洞：`approval_summary` 原先只渲染
  模型写的 `description`，不渲染 `arguments`，于是审批时看不出要把**哪个文件**发出去、
  把**哪个游戏**加购。散文是模型写的、参数才是将要执行的事实，两者必须都显示。

## 后果

**实测事实（2026-10-13，一次性探针 + 端到端任务）：**

- 兼容端点**接受 base64 data URL**。响应里 `image_tokens=154` 证明图片是被当作图像处理的，
  而不是静默退化到纯文本端点把图丢掉——后者是调研阶段最担心的失效模式。
- 两个模型都能正确读出图里的数字；端到端任务的最终回复与图片内容一致。
- **思考模式默认开启**：同一张图同一问题，关掉后 `completion_tokens` 从 73 降到 5。
- 错误形态：401 `invalid_api_key`、404 `model_not_found`。**400 与 429 的分支尚未实测**，
  `_classify_provider_error` 里已就地对未实测部分标注。

**代价与已知局限：**

- **数据外发是既定事实**：图片会离开本机到阿里云。已通过 `WRITE` 风险转化为「每次都要人过目」。
- planner 可能对简单问题选 `analyze_image`（实测复现：只问「图里是几」，它选了 Max）。
  接受这个折中——两个工具的语义区分（描述 vs 提问）对模型是可判断的，
  而档位本身仍不可由模型指定。
- **新增一条依赖边 `tools → providers/llm`**（工具层直接取模型）。这是本项目的第一次：
  以前 `tools` 不依赖 `providers`。看到工具里 import 模型层不要当成笔误——
  它没有绕过 `policies`，风险仍由注册表赋值。

**什么时候应该重新审视：**

- 千问换模型或换端点：只改 `config.toml`，本决策不变。
- 兼容端点不再支持 base64：需要换传输层（可能要新适配器），但**档位绑定设计仍然成立**。
- 若出现「必须让模型自己挑档位」的真实需求：那说明工具语义区分失效了，
  届时重新权衡，而不是悄悄加一个 `tier` 参数。
