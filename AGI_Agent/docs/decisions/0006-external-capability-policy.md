# 0006 外部能力接入策略：公开接口 + 人工登录

- 日期：2026-10-12
- 状态：已采用

## 背景

Agent 迟早要操作 Steam、微信这类**不属于自己**的外部系统。这些系统要么没有为自动化准备接口，
要么要求登录。需要一条能长期遵守的底线，否则每接一个新能力都要重新权衡一次，
而且很容易在「这样能省不少事」的诱惑下越线。

## 决策

三条规则，适用于**所有**外部能力：

**1. 不使用未公开或逆向出来的 API 端点。**
即使能显著省事也不采用。未公开意味着随时失效，且自动化访问可能违反服务条款。
外部能力一律走公开接口，或模拟人工操作。

**2. 需要登录的外部能力：不自动登录。**
采用「**人工登录一次 → 保存会话状态 → 复用**」的模式。代码中**不得出现密码、验证码
或任何自动登录逻辑**。

- 会话状态文件（cookies / localStorage / `user_data_dir`）**等同于凭据**：必须进 `.gitignore`，
  并且必须加入本地文件工具的**黑名单**，防止 Agent 读到自己或他人的登录凭据。
- 会话过期时**报错并要求人工重新登录**，不得尝试自动续期——自动续期意味着代码要接触凭据。

**3. 手写工具 vs 接入 MCP：判据是「流程是否固定」。**

| 情形 | 做法 |
| --- | --- |
| 流程固定、目标界面已知 | **手写窄工具**（内部可用成熟库，如 Playwright）。产出是人类可读的高层动作，能进入 `Plan` 被审批与审查 |
| 流程未知、需模型现场探索 | **接入 MCP**（如 Playwright MCP），把浏览器原语作为**另一种工具来源**登记进 `tools` 注册表 |

两者**不互斥**：同一能力可以先手写固定流程，日后按需再加 MCP 作为补充来源。

## 被否决的方案

- **用逆向出来的私有 API**（例如跳过 UI 直接调用 Steam 的购物车端点）：能绕开浏览器自动化，
  但违反规则 1，且随时可能静默失效——失败时不会报错，只会「什么都没发生」。
- **把账号密码交给 Agent 自动登录**：即使技术上可行也不做。一旦代码接触凭据，
  凭据就会出现在日志、异常栈和上下文里。
- **会话过期时自动续期**：同样意味着代码要持有凭据。
- **为每个小需求引入 MCP 层**：MCP Client 要付出子进程管理、协议握手、Node 运行时、
  跨进程调试的代价。像读文件这种 20 行就能手写的，不值得。**MCP 层应当被一个真实需求
  一次性逼出来并认真设计，而不是被小需求顺手带出来。**

## 后果

- 判断依据是**架构对齐**而非技术偏好：本图的审批发生在计划阶段，计划必须是人类可读、
  可审查的。若计划里写的是「点第 3 个按钮」，就既无法审批也无法审查。
- 代价是每次会话过期要人工重新登录一次。接受。
- **接入 MCP 的时机**：某能力已有成熟可信的第三方实现，且流程需要模型现场探索。
  在此之前不要为了「架构完整」而提前搭 MCP Client 层。
- 关于 Claude Code 的 Skill：那是 Claude Code 自身的能力，**不是本 Agent 运行时的能力**。
  本 Agent 是独立进程，不加载 Skill，不要把它当作工具来源。
