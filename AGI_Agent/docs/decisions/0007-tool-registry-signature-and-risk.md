# 0007 工具注册表必须公布参数签名，风险由 `policies` 赋值

- 日期：2026-10-12
- 状态：已采用

## 背景

因为不接受模型自选工具（ADR 0003），`planner` 必须**手动**产出工具名与 `arguments`。
实测出现的失败：planner 不知道微信发送工具的参数名，在连续三轮重规划里分别猜了
`recipient`、`contact`、`message`，最终失败——**猜参数名这件事本身就不可能靠重试解决**。

同时还有一个安全问题：计划是模型生成的，如果风险等级由模型在计划里自报，模型可以（也实测确实会）
谎报 `read` 来绕过人工确认。

## 决策

- **`ToolSpec` 必须公布参数签名**（一个 Pydantic 模型）。不公布签名，planner 只能猜。
- **风险等级由注册表定义、由 `policies` 赋值。不采信模型在计划里自报的 `risk`。**
- **`executor` 在调用前按签名校验参数**，让失败信息具体到字段名，
  而不是抛出无意义的 `TypeError`。
- **MCP 工具是同一个注册表的一种「来源」，不是另一套体系。** 将来接入 MCP Server 时，
  必须把 MCP 发现的工具**登记进 `tools` 注册表**（补齐 `ToolSpec` 的签名与风险等级），
  使 `planner` 看到的始终是一份统一的工具清单。

## 被否决的方案

- **不公布签名，让 planner 自由发挥**：实测已证明不可行，且失败模式是「反复重试并烧钱」，
  不是「一次报错」。
- **采信模型自报的 `risk`**：实测模型会把写操作谎报成 `read`。已实测会被覆盖为 `write`
  并正常触发审批。
- **为 MCP 工具另建平行的调用路径**：**这是最危险的一种重构**——那会让 MCP 工具绕过
  `policies` 的风险判定与人工确认，等于给 Agent 开了一扇没有门禁的后门。禁止。

## 后果

- 新增一个工具的成本提高了：必须同时写签名、写风险等级、补测试。这是**故意的**——
  工具是 Agent 能对世界造成影响的手段，不该随手加。
- 注册表成为 `planner` 能力的**唯一事实来源**：`planner` 看到的工具清单与 `policies`
  判定的风险等级来自同一个地方，不会出现「计划里有、策略里没有」的工具。
- 三个目录的职责由此固定下来，**必须保持分离**：`graph` 决定「怎么思考」，
  `tools` 决定「能做什么」，`policies` 决定「允许做什么」。
