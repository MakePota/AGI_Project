# 0013 不做微信（个人版）自动化

- 日期：2026-10-13
- 状态：已决定（可重审）

## 背景

`Memory.md` 曾把「微信（个人版 UI 自动化）」排为功能开发的下一站，理由是它是最贴近日常的
桌面操作能力。按守则 §2，动手前先做了 GitHub 与文档调研（微信的 MCP Server 与开源实现）。

调研结束时，用户决定**放弃**这个方向。这篇 ADR 记录的是**为什么放弃**，目的是让这个结论
不必被重新论证一遍——它是那种「三个月后一定会被重新提起」的决定。

当时的实际环境：本机装的是微信 **3.9.12.17**（个人版），另装有企业微信。

## 决策

**不做微信个人版自动化。** 已实现的能力不受影响，本决策只关闭这条路。

## 被否决的方案

调研把可行路线收敛成下面几类，**每一类都单独出局**：

| 路线 | 代表实现 | 机制 | 出局原因 |
| --- | --- | --- | --- |
| 网页协议 | wechaty 的 web puppet、itchat | 微信网页版 | **死路**：2017 年后注册的账号无法登录网页版；2022 年起的 UOS 补丁也已失效 |
| 注入客户端 | WeChatFerry 系（多数「微信 MCP Server」走这条） | 往客户端进程注入 DLL、hook 内部函数 | 违反 [ADR 0006](0006-external-capability-policy.md) 规则 1：这是典型的逆向私有实现 |
| 解密本地库 + 改内存 | `wechatauto-replica` | 提取 master key 解密 SQLCipher；往 `Weixin.dll` 写屏幕阅读器标志位 | 逆向 + 修改进程内存 + **接触凭据**，三条红线同时踩 |
| 破解闭源授权 | `wxauto4-plus` | 内存里 NOP 掉授权校验 | 侵权，不采用 |
| **驱动官方客户端界面（UIA）** | `wxauto`（免费版）、`pywechat` | 读控件树、模拟点击与输入 | **技术上可行且合规**，但见下方「为什么合规方案也被否」 |
| 截图 + OCR + 模拟点击 | 若干 MCP Server | 看屏幕、点坐标 | 合规但更脆弱、更慢，且需要视觉模型 |
| 企业微信官方 API | 官方 | 官方接口 | 完全合规，但**只能给同企业成员发消息**，够不到个人微信好友——不是本项目想要的那个能力 |

**为什么唯一合规的方案（UIA）也被否掉：**

1. **托底地基正在被拆。** 微信 4.x 改用 Qt + Chromium 自绘渲染，UIA 控件树整个消失；
   有项目记录「讲述人」那套让控件树显形的技巧在新账号上已经失效，只有部分老账号还行。
   也就是说：这套方案立在一个正在缩小、且不由我们控制的地基上。
2. **一次客户端升级就会让它报废**，于是「不许升级微信」会变成一条运行约束。
3. **账号存在被限制的风险。** 微信服务条款禁止自动化操作，这是实打实的、无法转嫁的代价。
4. 用户判断：**这个能力不值得为它承担上面的代价**。

## 后果

- 微信相关能力**不再排期**。`tools/builtin/fake.py` 里那个占位的
  `wechat.send_message` 仍是占位（它本来也只是用来验证审批链路的假工具），
  **保持原样**，不因为本决策而删除。
- **本决策可以重审。** 触发条件只有一个：出现一条既有稳定公开接口、又能覆盖个人微信的
  合法路径（例如官方开放了个人向的 Bot 能力，或企业微信推出能触达个人好友的合规通道）。
  到那时重新走一遍调研，而不是捡起这里被否掉的某条路线。
- 省下的这一小时调研不必重跑：上面的表格就是结论。
