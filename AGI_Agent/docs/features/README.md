# 功能文档索引

记录「**有哪些能力、各自怎么运转、要改它先看哪里**」。

它回答的是「这个东西当初是怎么设计的」。至于「为什么这样选」写在 [`../decisions/`](../decisions/)，
「项目整体长什么样」写在 [`../architecture.md`](../architecture.md)。

## AI 读取约定

**不要一次读完整个 `features/`。** 这些文档是为了「将来某一天被查到」，不是为了被全部记住。

1. 先读下面的目录表，判断哪 **1 篇**与当前任务相关。
2. 只打开那一篇。
3. 该篇链接到的 ADR 才需要继续读。没链接的，与本次任务无关。

一次任务读 1 篇功能文档 + 1-2 篇 ADR 是正常量。**如果你觉得需要读三篇以上才能开工，
说明索引表没写好**——那是个需要修索引的信号，不是需要读完所有文档的理由。

## 什么时候该写 / 更新

- 新增一个功能（哪怕只是加一个工具）
- 功能发生**行为上**的变化
- 发现了一处「不看文档就会踩」的坑

**改代码时同步改对应文档。** 文档腐烂没有别的解法——一份过期的文档比没有文档更糟，
因为它会主动误导。文档里唯一需要频繁更新的通常只有顶部那行「状态」。

## 内容边界：什么写进文档，什么留在代码注释

这条边界必须守住，否则同一件事会在两处出现，**必然有一处过期**：

> **删掉这段代码就失效的知识 → 写进代码注释。跨越多个文件才成立的知识 → 写进文档。**

- 进注释：某个选择器的依据、某个超时值为什么是 2500ms、这段归一化为什么要去掉符号。
  这些紧贴代码，改代码时必然看到。
- 进文档：这个能力为什么存在、和哪些模块协作、生产环境上的坑。
- **文档不重复注释的论证**，需要时链接到具体文件与行号。

### 「重复」的可操作阈值

完全避免重复是不可能的，目标是**不允许出现两条完整的推理链**：

| 类型 | 判据 | 是否允许 |
| --- | --- | --- |
| **论证级重复** | 同一因果解释在两处都**超过 2 行** | ❌ 禁止 |
| **摘要级重复** | 一处是完整论证，另一处只有 1-2 句结论 + 链接 | ✅ 允许 |

判断完整论证放哪一边，问一句：**这份知识在哪个时刻最需要被看到？**

- 改这段代码的人**必然**会打开这个函数 → 放**注释**（零检索成本）。
- 还没打开代码、甚至不确定要不要用这个能力时就需要 → 放**文档**。
- 不属于任何一个文件（例如「为什么不上 RAG」）→ 只能放 **ADR**。

> 现实检查：`local-file-tools` 与 `steam-tools` 的第一版都犯了论证级重复，
> 各自把代码 docstring 里的推理链抄了一遍。已改为链接。写文档时留意这个坑。

## 模板

```markdown
# 功能：<名称>

- 状态：已完成（YYYY-MM-DD）        ← 改动时主要更新这一行
- 涉及文件：`路径`、`路径`
- 相关决策：[0001 标题](../decisions/0001-xxx.md)

## 要解决什么问题
## 最终怎么做（人能读懂，不贴代码）
## 为什么这么做 / 被否决的方案
## 已知局限与坑
## 要改它先看哪里
```

篇幅随复杂度伸缩——`local-file-tools` 只需要几十行，`supervisor-graph` 会长一些。
**但「为什么这么做 / 被否决的方案」和「要改它先看哪里」两节必须写**，
它们直接对应「以后要改它，得先熟悉什么」。
